## 1. Purpose and users

The Orders module takes a salesperson's PI workbook (the BOE "Master" Excel Proforma Invoice) through review into a numbered
**Confirmed Order**, then carries the Order through production hand-off, amendments, PI revisions, documents and dispatch.
There is no other way to create an Order (the older Order Request workflow is retired, see 2).

| Who | What they do |
| --- | --- |
| Salesperson (sales team, `orders.create`) | Uploads a PI, fixes the draft, enters internal details (dates, middleman commission, salesperson, lead source, highlight remark), attaches/records payment, submits for review, proposes PI revisions/edits on their own Orders, uploads Design Files / Client PO, records fabric/finish approvals on their own Orders |
| PI approver (`orders.approve_order`, protected, per person) | Reviews PI: sends back, rejects, approves the PI decision, converts to a Confirmed Order, decides PI revisions |
| Advance-exception approver (`orders.approve_advance_exception`) | Decides "reduced advance" requests on PIs and Order-level "production below 40%" exceptions |
| Production authority (`orders.align_production`) | Legacy per-Order alignment; for Orders that have a handoff, alignment is the *result* of the Operations reviewer's acceptance only (see 6.7) |
| Operations reviewer (one person set in Control Center, duty `pi_handoff`) | Accepts / flags each PI version in force; acceptance aligns the Order for production; reviews Design Files / Client PO |
| Operations team (`users.team = 'operations'`) | Sees every Order; may move status running / on_hold / ready_for_dispatch |
| Active administrator (`users.role = 'admin'`) | Amend / cancel Orders, dispatch, approve/reject PI revisions (permission-gated since 20270120), delete PIs and Orders, Test Data Cleanup, number cycle |
| Finance verifier (`finance.approve`) | Verifies payments attached to PIs (see Finance dossier); no direct PI decisions |
| Owner only | Factory Focus selections, Order visibility scopes (via `is_orders_owner()` / `is_permanent_order_approver`) |

### 3.4 PI workbook parsing (`src/lib/pi/masterSheetParser.ts`)
- Sheet name must be `Master`. Header row 31 is fingerprinted (A31 Code, B31 Name, C31 Quantity, D31 "Dimension in inches & Shape" (the shorter "Dimension in inches" is also accepted, an alias in `PRODUCT_COLUMN_NAMES`, 2026-10-20), E31 Representative Image, G31 Material, H31 "Cost per piece (INR)", I31 "Total Cost (INR)", K31 Customization). Mismatch = refused (`TEMPLATE_FINGERPRINT_MISMATCH`).
- Product band rows 32-111 (80 slots B001-B080; column J = hidden item sequence). Header cells: B20 source order number, G20 creation date, **G21 Sales Person**, B22 BOE GST, G22 contact number (the **salesperson's** number), B25-B28 bill-to, G25-G28 ship-to, A113 order confirmation date, E113 dispatch commitment. Commercial footer I115 discount, I116 subtotal, I117 fabric, I118 packing, I119 transportation, I120 total before GST, I121 GST, I122 grand total. The footer is located by its column-G labels and may shift up to `MAX_FOOTER_OFFSET = 20` rows if proven.
- Blocking issues refuse the upload (product name/quantity/cost/item sequence/image missing or ambiguous or unsupported, SUBTOTAL/GST/TOTAL mismatches, GRAND_TOTAL_MISSING, FOOTER_NOT_FOUND, ...). **A missing salesperson (G21) is only a WARNING** (`PI_SALESPERSON_MISSING`) — it lands in an editable draft field. See contradiction C-3.
- Stated figures are never repaired: where quantity x rate disagrees with the line total both are reported and the workbook value is kept.
- `dispatch_commitment` (E113 prose) is NOT a due date. A due date is stored only if E113 is a real Excel date (>= `DUE_DATE_FLOOR = 2020-01-01`; serials below 61 or 1900-dated numbers are rejected) — `src/lib/orders/dueDate.ts`, mirrored in 20260922.

### 4.5 RLS idea
- Module entry is a RESTRICTIVE-style gate (`module_entry_open('orders')`) plus ownership/permission policies. `orders` SELECT: admin, operations team, `requested_by`, `assigned_to`, `orders.view_all`, plus the visibility-scope policy `orders_sales_scope_select` (20270221). Client roles have SELECT and column UPDATE(status) only; no INSERT/DELETE/TRUNCATE.
- A **visibility scope reveals Order detail, never money or authority**: Finance policies, `can_read_payment_as_participant`, `order_linked_payment_total`, document generation/retry and all authorisation helpers use the UNSCOPED rule (`can_view_order_unscoped`). `scopeIsNeverMoneyOrAuthority.test.ts` pins this.
- `order_submissions`: creator / submitter / assigned reviewer / `approve_order` holders / Finance verifiers on submitted+approved PIs (see `can_view_order_submission`; re-read the latest body before changing). The middleman commission lives in its own table so wider Orders authorities cannot read it.
- Several tables have RLS enabled with **no client grant and no policy** (Factory Focus, scopes, settings): reachable only through the SECURITY DEFINER RPCs.

### 4.6 Test-data machinery (important and easy to break)
- `test_data_cleanup_settings`: `enabled`, `permanently_disabled` (irreversible; `permanently_disable_test_data_cleanup('DISABLE TEST CLEANUP')`). While enabled, `stamp_test_data_flag()` stamps `is_test_data = true` on every new record at INSERT; the flag is immutable afterwards. **Dashboards, Factory Focus and revenue EXCLUDE `is_test_data` Orders** — if cleanup is still enabled when the first real Order is created, the dashboard looks empty and the flag cannot be flipped. Production state (verified 2026-10-21): **permanently disabled** by the owner at 11:52 UTC; the 8 Orders / 18 payment requests / 17 allocations stamped before that are re-labelled real by 20270328000300 (APPLIED 2026-10-21).
- Cleanup escape hatch is a GUC (`boe.cleanup_context`, read by `in_test_data_cleanup()`), transaction-local, set only by the executors after their gates. Never exempt "admins" in a guard — that exemption was exactly the hole closed by 20260705.
- Claim protocols (durable, token-based, storage deleted by the route, not in SQL): Test Data Cleanup (`begin_test_data_cleanup` -> `finalize`; admin chooses whether a deleted test Order's number stays spent, 20270217), module Reset (`begin_order_finance_test_reset`, 20261010), PI deletion, payment deletion.

- **A cancelled Order keeps its number for good (owner, 2026-10-31):** that number is never given to another Order. `change_confirmed_order_number` refuses any number an Order holds, and the two doors that could free one have no status check, so the Order page does not offer them on a cancelled Order (`canChangeOrderNumber`, `canDeleteOrder`) and both routes refuse with `CANCELLED` (`lib/orders/cancelledOrderLock.ts`; a failed read refuses too). The check is in the app, not the database. The owner considered reuse after asking twice and rejected it as confusing: do not propose it again.
- Confirmed Order number: stored **4 digits** (`0524`), permanent, never reused (cancelled Orders keep theirs); the UI shows the operational number without leading zeros (`524`, `formatOrderOperationalNumber`). The number is allocated **at approval inside the transaction** (`assign_order_display_number` -> `allocate_confirmed_order_number` under FOR UPDATE on the single-row `order_number_cycle`); a rolled-back approval rolls the cycle back. Since 20270114 a new draft reserves NOTHING; an existing reservation (one, 0525 in production per the migration header) is honoured and a reserved number is never reissued (`order_reserved_number_ledger`).
- **Change Order number (20270502000000, owner 2026-10-29 — APPLIED 2026-10-29, PR #502 merged as 217a69b2, deployed):** the one exception to "permanent". An active admin, from the ⋯ menu on the Order page (`ChangeOrderNumberModal` → `POST /api/orders/[id]/number` → `change_confirmed_order_number`), gives an Order a different number: digits only, 1–9999, stored four-digit; refused when any Order has it (`ORDER_NUMBER_CHANGE_IN_USE`), a PI Draft ever reserved it (`_RESERVED`: ledger or `reserved_order_number`), or it is at/above the cycle's next number (`_TOO_HIGH`; the allocator would later collide). Under the cycle row lock (cycle first, then the Order — allocation's order) it renames the Order, re-stamps its PI versions' `pdf_order_number` (same form each printed: `541`→`508`, `0541`→`0508`; owner: the PDF prints the new number), writes `order_activity_log` `order_number_changed` {from, to, old_number_is_next, next_number}, and — only when the old number was the newest (cycle next = old+1, no Order and no reservation at/above it, the cleanup "reuse" proof) — steps the cycle back so the NEXT Order gets the old number. Any other old number is left unused. Bypass: transaction-local `boe.order_number_rename` = that Order's id, read by the two re-emitted guards and cleared before the function returns. Product codes follow (display-time). Not rewritten: activity/amendment snapshots, notification titles, Meetings rows keyed by number text, Finance `legacy_order_no` allocations (pre-BOE One numbers such as 456/508 stay on their payments). Scratch proof: `supabase/tests/order_number_rename_pglite.mjs` (38 checks). Unit/text: `orderNumberChange.test.ts`.
- The next number is an admin decision (`set_next_confirmed_order_number`); cleanup returns only numbers it freed from the TOP of the range; the cycle returns to 1 only through `reset_confirmed_order_number_cycle()` (admin, finalized cleanup claim, zero Orders, no submitted/approved PI, no allocation pointing at an Order/PI; audited).
- Item codes: `BE0001`…; Order Product Code `<operational no>-BE0001` (e.g. `524-BE0001`, `524-BE0010`; **four digits, no dash after BE**, owner 2026-10-20, old and new Orders alike). `order_product_codes` stores only the integer `boe_sequence`; the string is built at display time by `formatBoeItemCode` / `formatOrderProductCode` (`lib/orders/orderProductCodes.ts`, `BOE_ITEM_CODE_DIGITS = 4`), so changing the width needed no data rewrite. Some SQL (`approve_order_pi_revision` line-matching jsonb, 20270116/20270120) still emits the old `BE001` label; the UI runs it through `normalizeBoeItemCode`. A retired code/item sequence is never reissued (edit revisions keep item ids so codes re-attach).
- **PI line numbers (2026-10-23, no SQL)**: a PI that is not yet an Order is renumbered BE0001…n in editor order on every Edit PI save (`buildEditProposal renumber`, apply mode only); Edit PI can insert a product anywhere. - **Customize image (2026-10-25, no SQL)**: Edit PI on a PI that is not yet an Order shows **Customize image** under each product that has a picture. ### 6.2 The advance / payment gate (replaced 20270227)
- Rule: required advance = **40% of Total before GST** (`STANDARD_ADVANCE_PERCENT = 40`), exact `numeric` (40% of 100.01 is 40.004; 40.00 does not meet it); shortfall rounded UP to the paisa; suggested standard amount = ceiling to the paisa. Worked example in the migration: pre-GST 1,20,000, GST 21,600, Grand Total 1,41,600, verified 48,000 -> exactly 40.00%.
- Total before GST = Subtotal (product value - discount) + fabric + packaging + quoted transportation ("as applicable" adds nothing). GST and the pre-GST total have NO column on `orders`; they live on the PI / PI version.
- Only **Finance-verified** allocations count (`finance_payment_status_is_verified`: `approved_unlinked`, `approved_linked`). A NULL / zero / NaN / negative base never passes (`value_known = false`).
- Approve is refused while ANY attached payment is still awaiting Finance (even if verified money >= 40%).
- Reduced route: below 40% attached payment (zero included) the submitter gives a reason (3 reasons above) -> exception `pending` -> approver decides; an approval belongs to one value basis (value epoch + PI version + verified amount) and goes `stale` if terms change. Money first, then the decision that stands in for money: if the PI reaches 40% while a request sits, approval takes the standard route.
- **Production needs 40% of the CURRENT Order value** verified, unless an admin-level approver approves production below 40% with a reason at **Order level** (`approve_order_advance_exception`, 20270205). The PI-level exception no longer starts production; it only lets the PI become an Order. An aligned Order that falls short (value raised, or verified money reduced) loses alignment in the same transaction (hold recorded, management notified).
- The old PI-level "Finance verification" step was removed (20261226); `verify_pi_finance_check` still exists but nothing requires it.

### 6.3 PI content rules
- Billing percentage: floor **35**, ceiling **100** (form, RPC, CHECK); undeclared is a real state (not 0, not 100); value = `total_before_gst` x percentage; read-only on the Order; refused rather than clamped.
- Must be present before finalization (`assert_order_submission_finalizable`): client name, creation date, salesperson, salesperson phone, client **city**, a fabric-responsibility answer (`boe` | `client` | `not_selected`; **NULL = unanswered, blocks**, no default), commercial terms. `commercial_terms_note` default is the standard BOE sentence for NEW drafts only (existing rows stay NULL so history is not rewritten; max `COMMERCIAL_TERMS_MAX_LENGTH = 2000`).
- Internal details (20270122/23): confirmation date and due date confirmed by Sales in the app (workbook values kept separately in `workbook_*`), middleman commission answer yes/no (+ who, + amount or percentage of a named figure) — required to submit; client never sees them.
- Order creation needs: salesperson, confirm date, due date, lead source (`approve_order_submission` args; Sales can prefill salesperson/lead source on the draft since 20270211, the salesperson is not required to submit; the lead source IS required to submit since 2026-10-20, client-side). **Since 2026-10-30 (owner) the approver is never asked for the salesperson:** Submit names the person submitting when Sales chose nobody (`nameSubmitterAsSalesperson` → `set_order_submission_sales_details`, run inside the send step after the dates save, no version check), and the approval dialog uses `orderSalespersonFor` = saved, else the one exact workbook-name match (`matchWorkbookSalesperson`), else `submitted_by`. A selector appears only when none of the three exists or the RPC refused the id. Lead source has no fallback, which is why Sales must choose it at Submit.
- Product lines: each needs item sequence + name + exactly one representative image; images PNG/JPEG/WEBP and must exist in storage.
- "Cost's meaning is a column": "Not applicable" and "Included" both add zero but are opposite answers.

### 6.4 PI decision vs Order creation
Two separate acts (20261119): `approve_pi_review()` stamps the PI decision (`pi_approved_by/at/submission_at`) and creates nothing; `approve_order_submission()` creates exactly one Order and stamps the decision itself if it is the first press. The PI decision is **stale** once the record moves (new `submitted_at`). One submission -> one Order in both directions (two partial unique indexes). A failed approval consumes nothing. Auto-approval (20261224 §5): a PI submitted by a holder of `approve_order` gets its PI decision stamped at submit; it is NOT a Confirmed Order and does not decide an advance exception.

- **Return to Sales / Close: deal lost (2026-10-29, 20270506000000, APPLIED 2026-10-29).** The reviewer's two buttons are relabelled (`REQUEST_CHANGES_BUTTON_LABEL` = "Return to Sales" → `needs_changes`, unchanged; `REJECT_BUTTON_LABEL` = "Close: deal lost" → `rejected`, still final). PI status labels read "Returned to Sales" / "Closed (deal lost)" (lists, history, salesperson dashboard, workflow panel). Closing now releases the PI's payment allocations and intents (Finance dossier §6.9); the close window shows the money on the PI (`piDecisionMoneyNote`). The owner's "Sales can resubmit after a rejection" is met by Return to Sales on the same PI; no transition out of `rejected` was added.
- **Approving opens the new Order (2026-10-30, owner request, no SQL, PR #510 merged as 33e4472e, deployed).** After **Approve PI & Create Order** or **Create Confirmed Order** succeeds, the PI Draft page goes straight to `/orders/[id]` with `router.replace` (Back from the Order goes where the PI was opened from), keeping the dialog on "Approving…" until it does; the PI is not re-read first. It stays on the PI (the old "Order created · number" screen with Open Order) only when `orderToOpenAfterApproval` (`lib/orders/finalApproval.ts`) says so: the RPC answer was unreadable, or the approver cannot SELECT the new Order under their own RLS (checked with one `orders.select('id')` after the RPC). `runAction` takes an optional `leaveFor` from its call for this. **Approve PI** alone (`approve_pi_review`) creates no Order and still re-reads the PI.

### 6.5 PI versions and revisions
- V1 is the document the Order was approved from. A later PI is always a **new version**; the in-force version changes only by admin-level approval (20270116): approve applies the revised parse through the one parser path, moves the Order's five amendable fields through `apply_order_amendment` (source `pi_revision`, with old/new values), supersedes the old version, and fires the operations-handoff trigger for the new version. Operations acceptance no longer stands between approval and the version being current.
- Proposing: PI owner holding `orders.create`, or admin; reason required. Approving / rejecting: `orders.approve_order` (permission-only). Rejection keeps the file and reason. One open revision per Order; items frozen while one awaits (legacy staging guards still exist).
- Edit PI (20270115): the proposal is built and priced by the server (`/api/orders/pi-edits`), never by the browser; kept in `order_pi_versions.proposal`; fabric responsibility, terms note, city, payment and billing terms and billing % are applied at acceptance.
- After an Order exists the PI's client, dates, figures, terms and lines refuse every write except a revision apply (and cleanup). Earlier admin edit doors keep working only on PIs that are not yet Orders.

### 6.6 Amendment model
Amendable fields (`AMENDABLE_FIELDS`): client_name, total_product_value, total_value, confirm_date, due_date, lead_source, notes (source comment says "eight", seven are listed). `created_by`/`created_at` frozen; `display_number` and the source provenance have their own guards; `status`, `notes` operational. NULL in a proposal means "leave alone" (neither door can blank a value). Reason mandatory; no-op refused. A change request approved against a newer amendment is protected (D6c, 20260818). Cancellation records the money received against the Order. Non-admin operations team can never write commercial columns (the wall: `orders_guard_amendable_columns`).
`assigned_to` is not amendable: a historical Order with no salesperson cannot be given one (open follow-up). `requested_by` = PI submitter, `created_by` = approver, `assigned_to` = salesperson (since 20261201); on `order_submissions` `assigned_to` = the PI reviewer and `salesperson_id` = the salesperson (20270211).

### 6.7 Operations handoff and production alignment
- Every time a PI version becomes in force (V1 at conversion; V2+ at admin approval) a handoff row is created for THAT version and addressed to the single configured reviewer (`order_operations_reviewers`, duty `pi_handoff`). With no reviewer it is recorded unassigned (`unassigned_reason = 'no_reviewer'`) and every active admin is notified; assigning a reviewer re-addresses waiting handoffs.
- **Acceptance aligns the Order** (alignment columns written in the same transaction); "Cannot accept" on an accepted version (reason required) takes it back; approving a later version RESET alignment to `not_aligned` until 20270401000000 (APPLIED 2026-10-22): from then an Order that is ALREADY aligned STAYS aligned (owner, 2026-10-22: a factory already making the order must not stop for a late customer change) and Operations answers the changed lines on the dashboard instead; an Order not yet aligned is unchanged (acceptance aligns). Money still wins: a revision that drops the verified advance below 40% opens an advance hold and removes alignment. `set_order_production_alignment()` on an Order with a handoff routes to the same decision, so being admin or holding `align_production` no longer aligns it.
- Alignment also requires the 40% rule (6.2) — refusal `ORDER_ADVANCE_BELOW_THRESHOLD`.
- **Respond and resubmit, remarks only (2026-10-27, migration 20270422000000, NOT APPLIED when written; dossier 23 records it applied 2026-10-28 with `db push --include-all`, not re-verified):** a flagged ("cannot accept") version can be answered without a new PI version. `respond_order_handoff_clarification(handoff, remark)` — owner of the PI or active admin (`can_propose_order_pi_edit`), 1–1000 chars — sets the handoff back to `awaiting`, keeps the objection (`clarification_*`) and stores the answer beside it (`clarification_response / _responded_by / _responded_at`), writes the Order event `operations_handoff_clarification_answered` and notifies the assigned reviewer (`order_operations_review_requested`). Nothing about the PI, the Order or its alignment changes. A new objection overwrites `clarification_*` through `decide_order_operations_handoff`; the older answer is then hidden (`respondedToLatestObjection`). UI: the **Respond and resubmit** button on the top notification (`OrderAttentionBar`), `RespondToOperationsModal`; the objection reason and the answer are shown in that notification's detail, no longer on the Documents card. The answer is shown from the Order's history (`latestHandoffAnswer`, payload of that event) because the page's handoff column list is pinned to `order_page_bundle`; the page therefore works before the migration is applied, only the button's RPC needs it. Rehearsed in a rolled-back transaction 2026-10-27.
- **Line flags before alignment (2026-11-12, PR #683 merged as `1278cc6a`, migration 20270616000000, APPLIED 2026-11-12 about 11:15 IST (after the 10:58–11:13 IST backup, alone, in one transaction; recorded with `migration repair`; 20270610000000 stays pending)):** the assigned reviewer can mark each line of the version under review OK / Comment / Cannot make with reasons (`price_low`, `quantity_low`, `complicated_design`, `size`, `material`, `other`), a required note (1–1000) and an optional suggested price. `flag_order_lines(handoff, lines)` validates (items must belong to `h.submission_id`; reviewer only), composes the reason with `order_line_flags_reason` (always ≤ 1000 characters; lines that do not fit are counted), then CALLS `decide_order_operations_handoff` unchanged: any `cannot_make` → `clarification_needed`, comments only → `accepted`. Flags are written AFTER the decision (its locks come first) and replace that handoff's earlier flags; a refused decision leaves nothing. Read with `order_line_flags_for(order)` (live handoff only, `can_read_order_detail`, never raises). UI: `OrderLineReview.tsx` (window + `LineFlagBand`), `useOrderLineFlags.ts` (self-loading, startup unchanged), rules `lib/orders/lineFlags.ts`, styles `lineFlags.module.css` (not globals.css). The button reads "Flag lines…" only when the function exists and the PI has lines, else "Cannot accept" as before. The Order's salesperson was ALREADY told of every flag/acceptance by `order_operations_handoff_notify` (20270401000000) with the reason as body. Not built (owner defaults): flagging after acceptance (use Withdraw), partial alignment, a structured Revise/Cancel/Stock design answer (phase 2). Traps: page DETAIL query pin 45 → 46 (the press-only `flag_order_lines` call); render tests that import `OrderPiSections` need `@/lib/testing/cssModuleStub`.
- **An approver's own PI revision approves itself (2026-10-27, no SQL):** `/api/orders/pi-edits` (propose mode) and the workbook door call `approve_order_pi_revision` / `/api/orders/pi-revisions/approve` for a proposer who holds `orders.approve_order`; a refusal leaves the version pending.
- Lock order for all handoff paths: `order_operations_reviewers` -> `orders` -> PI rows -> `order_operations_handoffs` (runbook has the table). Reviewer assignment takes `FOR UPDATE`; decisions take `FOR SHARE`.
- Order 0524's V1 was routed by a one-time, pinned-id data migration (20261230) that raises and writes nothing if any expectation changed.

### 6.8 Status and dispatch
See 4.2 and "Dispatch drives the Order's status" at the end (since 2026-11-03 the last dispatched piece sets `dispatched` itself). No payment gate exists on dispatch in code. ### 6.9 Documents
- Order documents version = a business fact (initial or after approved amendment); an attempt is a technical fact; a failed attempt creates no user-visible version; Order is document-ready only when BOTH Excel and PDF exist; the original uploaded PI is never overwritten. Claim lease 15 minutes; a run dying mid-flight leaves the row `claimed` (client treats stale after 15 min and offers takeover).
- Client-facing PDF must not reveal billing (`clientPdfNoBilling.test.ts`, `clientDocumentPrivacy.test.ts`).
- Design Files / Client PO: submit (1-25 files) -> admin decision -> operations decision; only operations acceptance makes a file current (derived: Client PO = latest accepted; Design Files = every accepted from latest accepted "replace"); never deleted; nothing yet for the main PI (it travels the PI-revision door). **Display rule (owner, 2026-10-19):** files sent with the PI (`stage = 'initial'`, `awaiting_operations`) are the Order's starting documents — the Documents card shows them in the Design Files / Client PO rows straight away (`sentWithPiOnFile`, used by `supportingRow` when nothing is accepted yet) and they never appear in the "Document changes" panel (`documentChanges` skips every `initial` row). That panel is for amendments and PI revisions only. The database status is unchanged: Operations' acceptance of PI V1 still marks them `accepted`. The Main PI row is a Notion-style record: title + one status pill with PI history and ⋯ on the right; the two dates (Uploaded, Approved) as properties; then the actions underneath — View PI (PDF) primary, Download original Excel secondary. The reviewer and file name are not shown (owner, 2026-10-19); only an unassigned/inactive reviewer is said, as a note. Product pictures sit BESIDE the Main PI (`.order-docs-main` is a two-column grid at ≥760px card width: Main PI grows, pictures take their content width), stacking under it when narrower. **Edit PI is in the page header** (`editPiAction` in page.tsx: same handler, `mayEditPi` gate and `EDIT_PI_BLOCKED_NOTE` disabled state), not in the Documents card. Below Design Files / Client PO, **Internal order details** (BOE only) lists what Sales filled on the PI: fabric responsibility, middleman commission, billing percentage, billing terms, payment terms (`orderInternalDetailRows` in `lib/orders/orderInternalDetailsView.ts`; dates, salesperson and lead source are not repeated — the summary panel has them). `billing_terms`, `payment_terms` joined `ORDER_PI_HANDOFF_COLUMNS`; the commission is read from `order_submission_middleman_commissions` plus `can_read_order_submission_commission` inside loadPiHandoff's existing Promise.all (DETAIL query count 41 → 43, no extra wait) and fails closed to "Restricted". Warnings that sit on the page (`.order-attention`, the Internal highlight banner, `.order-doc-changes`) are white cards with a 4px `#C48A1A` edge and a `#E6D2A0` border — the amber tints were too close to the `#F7F5F1` canvas; smaller notices inside cards use solid status tints (`.order-pay-notice` Working, `.order-custom` Blocked).

### 6.10 Deletion
- PI: statuses draft/needs_changes/submitted/rejected; owner or admin. Money always blocks: active allocation, pending intent, correction request. Releasable leftovers (20270315): reversed allocation of a payment that is soft-deleted, never approved, not in an applied intent. Submitted PIs carry document submissions whose rows are erased only inside that PI's purge. An `approved` PI is deleted as an Order.
- Confirmed Order: admin, typed number, not cancelled (see 6.1), no allocation/intent/payment-request link in any status (except releasable leftovers); Finance is never touched; ~20 tables of history are removed under the borrowed cleanup GUC in one transaction; storage is swept by the route AFTER; `order_deletion_log` is immutable.
- Approved verified payments are permanent (see Finance).

### 6.11 Factory Focus and visibility

Scopes per sales candidate: own / own + selected / all sales candidates (owner sets). Default everybody "own".

## 8. Decisions made and why (owner decisions)

- **Order Requests retired** (20261007): the only path to an Order is PI upload -> review -> approval, so `approve` and `can_be_order_assignee` options were removed from Access Control (an option that grants nothing is worse than none). `approve_order` was deliberately never `approve` so retirement took nothing away.
- **Two acts, not one**: PI decision vs Order creation; Order creation never automatic from a Finance RPC.
- **Advance base changed from Grand Total to Total before GST** (business agreement, 20270227): GST is tax, not value. Rounding rules unchanged.
- **Finance verification of the PI as a document removed** (20261226): per-payment verification already carries the fact.
- **Admin approval makes a revised PI current immediately** (owner 2026-09-25, 20270116); operations acknowledgement is a separate production-readiness question.
- **Alignment = Operations acceptance** (20261229); an older alignment can never make a newer unaccepted PI look ready.
- **Amendments only through audited doors**, via a transaction-local GUC rather than "exempt admins" (an exemption audits nothing).
- **Cleanup is a GUC, not an identity** (20260705/06), and test-data is stamped at INSERT, never a tick-box.
- **No reservation for new drafts; number assigned at approval** (20270114) so abandoned drafts burn nothing; existing reservations kept.
- **Equal admins / permissions over roles** (owner 2026-09-26): two admins of the PI->Order->Finance flow have equal authority; authority is a Control Center permission, nowhere in code. Exception: `orders.approve_order` is permission-only and unrevokable for the owner.
- **Admin delete of a Confirmed Order allowed** (reversal of the 2026-07 "Orders are permanent" rule) but only with no money attached and a typed number.
- **Owner-only Factory Focus and visibility scopes**; a scope reveals Orders, never money or authority.
- **Owner decisions of 2026-09-18 still to build**: dispatch gate (verified payment >= Order value - ₹1,000, otherwise salesperson requests "Dispatch on credit" with a reason; only admin / one named partner approves; "Ready for Dispatch" is never blocked and always notifies salesperson + Finance with the amount due); void / full refund / partial refund / customer credit / correction for wrong verified payments (admin or the named partner by permission, one person enough, refund records date/amount/mode/reason and reduces Order paid and product values; bounce not needed); "Next action" column on the PI list only + a "My pending actions" view; Orders list columns (Order no, Client, Salesperson, Order value, Confirm date, Due date, Fabric/finish status; no payment columns); fabric and finish tracked **per product** with pieces approved ("Fabric 6/10 pcs"), "Fabric sent by customer" enabling quantity per piece with area (Full piece / Seat / Back / Custom), quantities taken from the PI workbook sheet "Packing cost and Fabric Cost" (H fabric per pc, I total), a customer-fabric label PDF (Order no, Product Code, Fabric Code, quantity in metres, area), salesperson REQUESTS quantity and the owner or partner ENTERS it; staged payments optional with no reminders; lead source asked separately (now done via 20270211); a payer name and a Sample Order type are NOT wanted; "Quotation -> PI is later". Memory marks these **(unverified, from memory)** — none exist in code.
- **Changes during manufacturing (owner, 2026-10-22).** Late customer changes arrive as an approved PI revision. Operations (the assigned reviewer) answers EACH changed line ✔ can do / ✖ cannot do / ? needs discussion, plus Accept all / Reject all; a note is required on ✖ and ?. The answers are advice to the approver, who decides with the customer, and appear in the approver's dashboard ("Operations responses"). The order stays aligned whatever is answered.
- **Test login kept; no second hard admin; owner sets the first Order number** (go-live decisions, from memory).

Part sent and the rest fully ready (Operations pressed Ready for Dispatch) = **Ready for Dispatch**. "Part dispatched" is NOT a status: it is a line under the status, so the three lists stay the three the owner described.
- **The roll-up.** `order_dispatch_sync_status(order)` (internal, no client grant) closes an Order (-> `dispatched`) when `order_dispatch_pieces(order).all_sent` (every PI line's dispatched lots add up to its quantity; quantities lowered below what left are clamped; lines with no quantity are ignored; planned lots count for nothing) and the Order is Running, On Hold or Ready for Dispatch. It writes the same `status_changed` Activity row the Order page writes (`payload.to = 'dispatched'`, so the Operations dashboard's "dispatches by date" counts it) plus `source = 'dispatch'`, `dispatched_on`. It UNDOES a close only when the Order's latest `status_changed` row is its own (`source = 'dispatch'`): an admin removing or lowering a dispatch puts the Order back to the status it had (`payload.from`); a Dispatched an admin set by hand is never touched.
- **When it runs.** Two DEFERRED constraint triggers, so it reads the finished state at commit: on `order_dispatch_lots` (insert / update / delete: recording, marking a planned lot dispatched in the Payment plan, the admin change, an admin delete) and on `order_pi_versions` going `approved` (a revised PI that lowers a quantity to what already left closes the Order; one that raises it reopens an automatic close). A value change on a dispatched Order is still refused by `approve_order_pi_revision`.
- **The status graph** (`orders_enforce_status_transition`, re-emitted): `ready_for_dispatch -> running` is new (and in the Order page's `TRANSITION_GRAPH`, which must mirror it); inside the roll-up context the graph is its own and the role gate is skipped (a salesperson recording the last piece may not change a status by hand); cancelling an Order with anything dispatched raises `ORDER_PART_DISPATCHED` (worded in `amendmentErrorMessage`; the way to stop the rest is a revised PI down to what was sent, which closes the Order). The Order page's Change Status menu hides Cancel once `dispatchLedger.dispatched > 0`.
- **The list.** `/orders/all` OPENS ON RUNNING (`status` default 'running'; All orders = `?status=all`, the only value written). A search, or `?ops=awaiting`, looks at every status instead (`widened`, `effectiveStatus`): the pressed card says All orders, a blue note says "Searching every status…" with Back to Running. Running and All orders are not "filters" (no Clear filters). An empty Running view says "No running orders right now." and offers All orders. **Factory Status** = `factoryView()` in `lib/orders/orderListValue.ts`, drawn by `app/orders/all/FactoryCell.tsx`: words from the status (Not Aligned / Aligned only for Running; On hold; Ready for dispatch; Dispatched), the line from `orders_dispatch_progress()` — "Part dispatched · 22 of 74 pcs", "74 pcs · last 28 Oct" on a Dispatched Order, "22 of 74 pcs recorded" on one an admin closed by hand, "All dispatched · 74 pcs" if everything left but the roll-up has not run. Every order of ClickUp's Running Orders list (521: 54 running, 10 ready for dispatch, 20 on hold, 19 cancelled, 418 dispatched) is copied out and kept: first as a LOCAL BACKUP (a one-off export with the owner's ClickUp token; folder `~/BOE-Development/backups/clickup-running-orders/<date>/` holding `orders.xlsx`, `orders.json`, `manifest.json` with sha256, `tasks/<id>.json` (ClickUp's raw answer) and `files/<order> [<id>]/<IST upload date>_<name>`; 1,064 files, 4.3 GB, checked against ClickUp's counts and sizes, every file re-read), then as DRAFTS in the app so the owner can test them before anything moves to Confirmed Orders. Customer data: that folder never goes in git (the repository is public).
- **Where.** Sidebar "Draft Orders (ClickUp)" (Administrators only; nav key `clickup`, `activeOrdersNav` must name it or the path reads as an Order record). `/orders/clickup`: status tabs (Running orders, Ready for dispatch, On hold, Cancelled, Dispatched, All) with counts, search, **Download Excel** (three sheets like the backup's: Orders, Files with upload dates, Comments) and **Import from backup folder**. `/orders/clickup/[id]`: every ClickUp field (client, phone, billing, shipping, value, dates, fabric / finish status), description, **files with upload date, uploader, size and Download**, checklists, comments with dates, status history. `/orders/clickup/import`: the folder import.
- **Not Orders.** A draft has no order number of ours, no payment, no dispatch, no notification and no PI, and nothing reads the table except these pages. "Move to Confirmed Orders" is NOT built (owner: test first, then decide).
- **Data.** `clickup_draft_orders` (one row per ClickUp task, unique `clickup_id`; `fields`, `comments`, `files`, `checklists` as jsonb; generated `file_count` and `comment_count`; `order_no` is not unique: ClickUp has order 130 twice) and the private bucket `clickup-draft-files` (`<task id>/<file id>`; ClickUp's file ids look like `<uuid>.xlsx`). RLS on, NO policy, nothing granted: closed. Every read and write is `/api/orders/clickup-drafts/*`, which asks `users.role = 'admin'` first (`guard.ts`) and then uses the service role (the same closed-table pattern as Customize image learning). Routes: list (`?full=1` for the Excel), `[id]`, `[id]/files/[fileId]` (302 to a two-minute signed link that saves under the original name), `import` (two steps). Words and rules in `lib/orders/clickupDrafts.ts`.
- **Import.** Chrome or Edge (`showDirectoryPicker`). The page reads `orders.json` from the chosen folder, then per order: `sign` (the server lists what is already stored under the task and hands signed upload keys only for files missing or of a different size; paths are built server-side from ids) → the browser sends the files straight to storage (a body over 4.5 MB never reaches a route; the largest file is 48.2 MB) → `save` (the server lists again, refuses unless every file is stored with the size the order lists, then upserts by `clickup_id`). The row is written last, so it never points at a missing file, and running the same folder again fills only what is missing.
- **Traps.** (1) ClickUp file ids contain a dot (`<uuid>.xlsx`): a plain-id check refused every real order. Found only by running the validator over the REAL backup; invented fixtures had passed. (2) A Next route file may export only handlers and config (a pin test reads every route file). (3) Orders 492, 466, 264 and 130 (dispatched) have no file in ClickUp. (4) The ClickUp activity feed lines, linked tasks and tracked time are not in the copy. (5) New table + bucket: the owner's backup rule says back up first.
- **Proof.** `clickupDrafts.test.ts` (23 tests: IST times, ids, paths, what a save accepts and refuses, caps, Excel, admin-only pins, the migration's text), `supabase/tests/clickup_draft_orders_pglite.mjs` (17 checks on in-memory Postgres: the REAL migration applies twice, counts, shape check, one row per task, closed to anon and signed-in, the self-check stops a policy or a public bucket), the real backup through `parseSaveOrder` (521 of 521 accepted, 1,064 distinct paths, none missing on disk), nav pins in `moduleNav.test.ts` and `orderRequestRetirement.test.ts`, both migration ledgers. ## PI change marker on Confirmed Orders (2026-11-14, Operations' request, branch `feat/orders-change-highlight`, PR pending, no SQL)
- **Ask.** Nitish (Operations): highlight an order in the Confirmed Orders list when its PI was changed and the change waits for somebody, and keep it until that person acts (accept, reject, ask for changes).
- **What it is.** STATE, not a notification: the same for everybody who can open the Order, and nobody reads it away. The blue "New update" row tint is the other thing (one reader's unread `notifications` row, gone when they open the Order). A change means PI version 2 or later; every new Order starts with V1 awaiting Operations, which "Not Aligned" already says.
- **Four states, newest step first** (`lib/orders/piChangeMarker.ts`, `buildPiChangeMarkers`; the same rules as the Order page's attention strip): (1) a pending revision in `order_pi_versions` → "PI changed · awaiting approval"; (2) the approver sent it back (`salesReturnStage`, via `loadOrdersWithSales`) → "· with Sales"; (3) live handoff `clarification_needed` → "· Operations asked for changes" (red; waits on Sales); (4) live handoff `awaiting`, version ≥ 2 → "· awaiting Operations". One marker per Order; a pending revision wins over older steps. Deciding any step (approve / reject / accept / answer the lines / flag / Sales responds) moves or removes the state by itself, so nothing is cleared by hand.
- **Where.** A pill under the Factory Status word (the Project code column is 116px, too narrow for the words), an amber (red for "asked for changes") 3px row edge and a faint tint; on a phone, a line on the card. A cancelled Order (a gap row) shows nothing. `app/orders/all/PiChangePill.tsx`, rules `.has-pi-change*` / `.orders-pichange*` in `globals.css` after `.has-update`.
- **Data.** No SQL. `loadPiChangeMarkers(supabase)`: `order_pi_versions` `status = 'pending'`, and `order_operations_handoffs` live (`superseded_at is null`), `awaiting` or `clarification_needed`, `version_number >= 2`; both RLS = `can_view_order`, so a reader sees only Orders they can open. Issued inside the page's one `Promise.all` (`loadPiChanges`) and again on Refresh; a failed read draws no marker. Reads sit in the lib file, so `orderStartupShape.test.ts`'s file-wide count for the page stays 8 (comment added there).
- **Not built (on purpose).** A "show only these" filter (the dashboard's Changes to review and `?ops=awaiting` exist), floating marked rows to the top, a "waiting 3 days" line, change requests and Design Files / Client PO changes.
- **Tests.** `lib/orders/piChangeMarker.test.ts` (precedence, the two reads' filters, a failed read, the page wiring); the two Refresh-line pins in `factoryStatusView.test.ts` and `orderListValue.test.ts` now include `loadPiChanges()`.
- **Not proven.** Not seen on a screen (signed in or on a phone); no real revised PI exists in production to look at (see trap in section 9 on the Operations dashboard); the pill's wrapping in the 21%-wide Factory Status column is unmeasured.
