## 2026-10-19 — Console "preloaded but not used" warning: other modules are warmed on intent, not on load (PR open) · no migration
- Root cause: the Modules launcher prefetched every module route in an effect on load, and Quick Actions prefetched /exhibition-leads/add and /finance/expenses/new. A prefetched route brings its stylesheet, which the browser preloads; the current page never applies it, so Chrome logged "was preloaded using link preload but not used within a few seconds" for Control Center, Inventory and Exhibition Leads CSS, while the burst of requests competed with the page's own data.
- Fix: Module cards (not in edit mode) and Quick Action buttons now call router.prefetch on pointer-enter, focus and touch-start only. Same-module warm-ups (Dashboard -> /tasks/my, /notifications, /modules) are unchanged.
- Guard: src/app/modules/intentPrefetch.test.ts. Not verified in a browser against production; the owner should check the console after deploy.

## 2026-10-19 — Correct a pending payment that is already attached to a PI (#360) · migration 20270322000000 → APPLIED to production 2026-10-19 (applied alone; the two 20270321 migrations were left unapplied)
- Follow-up to #357. Its Edit buttons opened the form, but saving a payment recorded from a PI failed ("could not be submitted"): that payment carries an ALLOCATION (written by `record_pi_submission_payment`), and `edit_payment_request` only knew the intent model — it refused it (`PAYMENT_EDIT_ALLOCATED`, or `PAYMENT_BELOW_ALLOCATED` / `INTENT_EXCEEDS_PAYMENT` when the amount moved), and the form drew it as a Suspense Entry.
- New `20270322000000_finance_payment_edit_reallocates.sql` restates `edit_payment_request` (same signature and grants). An UNVERIFIED payment with EXACTLY ONE active allocation is now correctable: the destination is locked to the allocation's target (`PAYMENT_EDIT_DESTINATION_LOCKED`); an allocation covering the whole payment follows a changed amount — reversed with a reason ("Payment corrected before verification: X changed to Y.", row kept with who/when) and re-created on the SAME target through `allocate_payment_to_target_internal`, one transaction; a partial allocation stays and the amount may not fall below it; several allocations are refused by name (`PAYMENT_EDIT_SPLIT_ALLOCATED`). The PI is locked before the payment (project lock order). Verified payments are still refused. Permission unchanged: the submitter or an admin.
- Edit form (`paymentRequestsEdit.tsx`): reads the active allocation when there is no intent (`loadPaymentAllocation`), shows the real destination locked, says when the attached amount will follow, blocks a split payment. `paymentEntryErrorMessage` now says these refusals in words.
- Proof: `supabase/tests/run_payment_edit_reallocates_suite.sh` (disposable Postgres; production allocation guards installed verbatim by `_payment_edit_reallocates_extra_schema.sql`; defect reproduces before, 8 groups of assertions pass after, migration applies twice in one transaction); `run_payment_entry_edit_race.sh <host> --with-20270322` (edit vs approval, both directions); `payment_custody_and_modes_assertions` still pass with the migration applied.
