## 2026-10-28 — Backups: pg_dump step for the tables the service role cannot read (PR pending) · no migration
- **Owner request.** Close the gap: five relations (three tables, `order_advance_exceptions`, `order_advance_exception_voids` and `order_advance_holds`, and two views, `finance_payment_destinations` and `finance_received_payments`) were never in the export because the service role is denied them. They were covered only by Supabase's own daily backups.
- **What.** `backup-database.mjs` step 2b: when `BACKUP_DATABASE_URL` (the Supabase session-pooler URI, with the database password) is in `backups\.env.backup` and Docker is running, the three real tables are dumped with `pg_dump` inside a container into `pg-dump-restricted-tables.sql.gz.enc` (same encryption as the rest). The two views are rebuilt from exported tables, not dumped (a first live run on 2026-10-28 aborted because one of them was treated as a table; fixed). `BACKUP_PG_IMAGE` (optional) picks the image; its `pg_dump` must be at least the server's major version (production is Postgres 17.6; the image `public.ecr.aws/supabase/postgres:17.6.1.171` is already on the owner's machine, so nothing needs downloading). `verify-backups.mjs` now shows `pg_dump: …` for the covered tables.
- **Safe by design.** Any pg_dump problem (no URL, Docker off, wrong password, a table missing from the dump) is a warning only: the tables stay listed as NOT COVERED and the daily backup still succeeds. The password is redacted from log lines.
- **Found and fixed on the first live runs (2026-10-28).** (1) The database password contains an `@`, which must be written `%40` in the connection address. (2) `finance_payment_destinations` is a view, not a table, so dumping it made the whole step look failed: both views are now listed as "rebuilt from exported tables" instead of "NOT COVERED" (their sources are in the export). (3) The row counter used a pattern that, for an EMPTY table followed by other data, ran into the next table's block and recorded 9 rows for `order_advance_exception_voids` (really 0); it is now a line-based `countCopyRows` in `lib.mjs` with a test (`scripts/backup/lib.test.mjs`) that covers exactly that case.
- **Proof.** Live run: `pg_dump OK` for the three tables; the dump was decrypted and read back (every table has its CREATE and COPY block; the row counts match the manifest); verify-backups passes. Earlier: syntax checked; the container call proven with a fake host (clean failure, nothing printed but the host error); the row-count parsing run on a sample dump (2 rows, an empty table as 0, a missing table detected). Ran against the live database with the owner's `BACKUP_DATABASE_URL` (see above).
