Process consultant review — BOE Phase 1

12 real-world failure modes · Preventive design · Hardened scope

1 + 2. Likely problems & design solutions

1

Employees avoiding updates

The most common failure in any new process system. People will open the app, see a task, and close it without updating — especially if there is no immediate consequence and the interface requires effort.

Design solution

The daily update must require zero typing. Replace the update flow with a 3-second action: open notification → see task → tap one status button → done. No text, no form, no confirmation screen unless marking complete. Additionally, build a "daily digest" notification at a fixed time (e.g. 6 PM) that lists only the tasks needing an update — not all tasks, not all notifications. One focused prompt per day. Management's dashboard must visibly show "who has not updated today" as a named list — social visibility is a stronger motivator than app notifications.

Rule to add: A status tap with no text counts as a valid update and resets the escalation clock. Typing is optional, never mandatory for a daily update.
2

Fake or meaningless updates

"Working" tapped every day for 10 days on a task that has clearly not moved. The escalation clock resets, management sees green, but nothing is actually happening. This is the most dangerous failure — it creates a false sense of control.

Design solution

Introduce a "stale progress" detector. If a task has received the same status ("Working") for 5 or more consecutive updates without any change in status or note, the system automatically flags it with a "No visible progress" indicator — separate from the standard escalation logic. This flag is visible to the creator and manager but is not an alert to the assignee — it triggers a quiet manager review, not a panic notification. Also, if a task deadline passes while status is "Working" or "Started," it immediately enters Overdue — the assignee cannot self-mark it as on-track once the deadline is crossed.

Rule to add: Same status for 5+ consecutive days on a non-daily-update task auto-flags as "stale." Managers see this on their Team view with a distinct indicator.
3

Duplicate tasks

Two managers create the same task for the same person on the same day — happens constantly in verbal-culture companies transitioning to systems. The assignee gets confused, updates one, ignores the other, and neither creator has full visibility.

Design solution

On task creation, before submission, the system does a soft-match check: if an open task assigned to the same person contains 3 or more of the same words in the title, show a warning — "A similar task may already exist" with a link to review it. Do not block the creation — just surface the potential duplicate so the creator can decide. Additionally, create a simple "task already exists" search on the creation screen: one search field that queries open tasks by keyword before the form is filled. This prevents the problem at the source rather than fixing it after.

Rule to add: Duplicate detection is a soft warning, not a hard block. The creator decides. But every creator must see the warning before submitting.
4

Vague task titles

"Follow up," "Check on order," "Call client." These titles are useless in a task system. The assignee does not know what action to take, and the creator has no basis for reviewing completion quality.

Design solution

Enforce a minimum title structure through a UI hint, not a technical validation. When the title field is focused, show a greyed-out example: "e.g. Call Ramesh at Leela Hotel — confirm upholstery spec by Wednesday." Below the field, show a live character count with a soft minimum of 20 characters — if the title is under 20 characters, show a yellow hint: "Be more specific — who, what, and by when?" Never block submission. Additionally, build 5–6 task title templates for common BOE task types: "Follow up with [client] about [topic]," "Confirm [item] with [vendor/team]," "Prepare [document] for [purpose]." One-tap templates reduce typing while enforcing structure.

Rule to add: Task title templates are mandatory to build into the creation screen. They serve as education and enforcement without friction.
5

Seniors delegating but staying accountable

A senior assigns a task to a junior. Junior fails to complete it. Senior says "I delegated it." Junior says "I was not sure what to do." The system must make clear who owns the task at every moment and who is still responsible for the outcome.

Design solution

Delegation must require an explicit acceptance step from the new assignee — not just a notification. When a task is delegated, it sits in a "Pending acceptance" state. The new assignee sees it highlighted and must tap "Accept task" or "Decline with reason." If declined, it goes back to the delegator. Until accepted, the original assignee's name remains on the task with a "Delegating…" badge — they are still on the clock. Once accepted, the full ownership chain is displayed on the task: Created by → Originally assigned to → Delegated to (current owner). This chain cannot be deleted. Managers can see the full chain on any task.

Rule to add: Delegation is not complete until the recipient accepts. Escalation clock does not transfer to the new assignee until acceptance. Original owner owns the delay.
6

Urgent unplanned tasks disturbing planned tasks

A client calls with an urgent requirement. Management creates a new high-priority task for a person who already has 4 active tasks. The new task jumps to the top, the old tasks get silently deprioritised, and no one has discussed what gets dropped.

Design solution

When a High priority task is created for a person who already has 2 or more open High priority tasks, show the creator a load warning: "Rahul already has 3 high-priority tasks. Assign anyway, or would you like to reassign one?" This is a friction point placed specifically at the creator — the person creating the new urgent task must consciously acknowledge the load impact. Additionally, introduce an "Urgent" flag separate from the priority system — a task can be Urgent without being permanently High priority. Urgent tasks appear with a distinct red strip on the assignee's task list and push a direct notification, but they do not affect the escalation timer of existing tasks.

Rule to add: Urgent flag is a one-time alert mechanism, not a permanent status. It cannot coexist with the daily update rhythm — it bypasses it once, then falls into the normal system.
7

Tasks stuck because another person is blocking them

An assignee sets status to "Waiting" or "Blocked" — but does not name who or what is blocking them. The task sits there. No one acts. The escalation timer still runs. The assignee gets penalised for someone else's delay.

Design solution

When an assignee selects "Waiting" or "Blocked" status, the app must require one additional field before saving: a Blocker field — either tag a team member (from the people list) or type a one-line reason (e.g. "Waiting for client to send fabric sample"). This is the only mandatory text in the entire system. The blocker name or reason appears on the task card and on the manager's Team view. If a team member is tagged, they receive a notification: "You are blocking [task name] — assigned to [name]." The escalation timer pauses for "Waiting" status but not for "Blocked" — Blocked is a hard stop that requires manager intervention.

Rule to add: Waiting = external block (timer pauses). Blocked = internal block (timer continues, manager alerted). These must be two distinct statuses, not one.
8

Overdue tasks becoming normal

After a few weeks, people accept that tasks will always be overdue. The red "Overdue" badge loses its meaning. People stop caring. Management stops reacting. The system becomes wallpaper.

Design solution

Overdue tasks must require a mandatory deadline revision or escalation — they cannot just sit overdue indefinitely. When a task goes overdue, the assignee sees a prompt once per day: "This task is overdue. Request a deadline extension or mark as Blocked." If they request an extension, the creator is notified and must approve the new deadline. If neither action is taken within 24 hours of going overdue, it automatically escalates. This forces a decision — tasks cannot exist in a passive overdue state. Separately, management's weekly digest should show a "chronic overdue" metric — tasks that have been overdue for more than 3 days — to prevent normalisation at the organisational level.

Rule to add: An overdue task that receives no action within 24 hours auto-escalates regardless of the standard 72h timer. Overdue tasks have their own faster escalation lane.
9

Employees claiming they were not informed

"I never got the notification." "No one told me." This is the most common verbal defence when a task is missed. In a WhatsApp culture, it is often true — messages do get buried. In a task system, it must be impossible to claim.

Design solution

Build a mandatory acknowledgement system. When a task is assigned or delegated to someone, it appears in a special "Unacknowledged" state with a distinct visual treatment. The assignee must tap "I have seen this task" — a single button — within a set window (e.g. same business day or 4 hours during working hours). Until they tap it, the task shows as "Unacknowledged" to both them and the creator. If 4 hours pass without acknowledgement, the creator gets a gentle alert. The tap timestamp is permanently logged. This is the digital equivalent of signing a receipt — it eliminates the "I wasn't informed" defence completely and with zero ambiguity.

Rule to add: Acknowledgement is a single tap — not a form. The timestamp is shown on the task detail to both parties. It cannot be deleted or edited.
10

Management needing clear proof of responsibility

When a client complaint arrives, or an order is delayed, management needs to answer: who was responsible, what did they do, and when? Without this, accountability conversations become verbal arguments with no resolution.

Design solution

Every task must have a permanent, append-only activity log — displayed on the task detail screen in reverse chronological order. Every action is recorded with the actor name and timestamp: task created, assigned, acknowledged, status changed, delegated, deadline changed, escalated, completed. Nothing can be deleted from this log. No editing of past entries. Separately, management should have a "Task history export" — a simple list view of all completed and overdue tasks for a given person or period, filterable by date, team, or status. This is not a complex report — it is a scrollable list that can be screenshotted or shared. This feature exists not for daily use but for accountability conversations when things go wrong.

Rule to add: The activity log is read-only, permanent, and visible to all parties on the task. It is the single source of truth for any dispute.
11

Too many notifications causing people to ignore the app

If the app sends 8 notifications a day, people start ignoring all of them within two weeks. Notification fatigue is the number one reason task apps get abandoned in non-tech companies.

Design solution

Enforce a strict notification budget per user per day — maximum 3 push notifications from the system (not counting direct messages). Priority order: (1) New task assigned to you, (2) Task blocked — you are the blocker, (3) Escalation reached. Everything else — reminders, status updates from others, acknowledgement prompts — goes into a single daily digest notification at a fixed time set by management (e.g. 9 AM summary + 6 PM reminder). Notifications from the system must never be sent between 9 PM and 8 AM. Users should not have individual notification settings in Phase 1 — this creates inconsistency. Management sets the notification schedule for the team once, and it applies to everyone.

Rule to add: 3 real-time push notifications maximum per day per user. Everything else batched into the daily digest. No late-night notifications. No per-user customisation in Phase 1.
12

Sales and operations teams using the app differently

Sales tasks are relationship and timing driven — "Follow up with Leela Hotel by Thursday." Operations tasks are process and dependency driven — "Get quality check done before fabric dispatch." A single rigid task format serves neither well.

Design solution

Do not build separate modules in Phase 1. Instead, use the task type field plus title templates to serve both teams. Sales team gets templates like: "Follow up — [Client] — [Topic]" and "Proposal to be sent — [Client] — [Date]." Operations team gets templates like: "Quality check — [Item] — before [Event]" and "Vendor coordination — [Supplier] — [Requirement]." The underlying task structure is identical. The difference is only in how the creation screen guides each team at input time. In Phase 2, you can introduce team-specific task views and filters once you have real usage data showing where the differences actually matter.

Rule to add: Task templates are team-specific (Sales / Operations / Design / Purchase) but task data model is unified. One system, guided entry.

3. Rules that must be built into the app

Acknowledgement is mandatory. A task does not enter the escalation clock until the assignee acknowledges it. Unacknowledged tasks have their own alert to the creator after 4 working hours.
Delegation requires acceptance. Ownership does not transfer until the new assignee taps "Accept." Until then, the original owner is still accountable.
Waiting and Blocked are separate statuses. Waiting pauses the escalation timer. Blocked does not — it requires a named blocker and triggers a manager alert.
Overdue tasks escalate faster. Standard escalation: 72 hours of silence. Overdue escalation: 24 hours of no action after the deadline passes. Two separate timers.
Activity log is permanent and read-only. Every action on every task is logged with actor name and timestamp. Nothing can be edited or deleted from the log.
Maximum 3 real-time push notifications per user per day. System-set schedule, not user-customisable. Late-night notifications are blocked system-wide.
Same status for 5+ consecutive days triggers a "stale" flag visible only to the manager — not an alert to the assignee. Quiet signal, not a punishment.
Duplicate warning is mandatory before submission if a similar open task exists for the same assignee. It is a soft warning — not a hard block — but it cannot be dismissed without the creator seeing it.
Overdue tasks cannot self-resolve. An assignee cannot mark an overdue task complete without either the creator seeing it or a deadline extension being approved first.
Urgent flag is a one-time mechanism. It sends one direct push notification and creates a red visual indicator. It does not change the escalation timer or the priority ranking permanently.
High-priority load warning is mandatory when assigning a third High-priority task to someone who already has two open High-priority tasks. Creator must acknowledge the load before submitting.

4. Features to avoid in Phase 1

Comments / chat inside tasks

This replicates WhatsApp inside the app. People will have side conversations, lose context, and avoid the structured update system. Defer to Phase 2 — notes field is sufficient.

Subtasks or task dependencies

Adds enormous complexity to accountability tracking. If two tasks are related, the note field is enough. Dependency mapping belongs in a later phase once teams have mastered basic task hygiene.

File attachments on tasks

People will attach large files, the app becomes slow, and the feature becomes a crutch for vague task titles ("see attached for context"). All context should be in the title and note fields.

Custom notification settings per user

Creates inconsistency across the team and gives individuals the ability to opt out of accountability. Management sets the schedule for everyone. This is non-negotiable in Phase 1.

Task categories / tags / labels

In a team that is not yet used to updating tasks at all, adding a classification layer creates unnecessary friction at creation time. Templates already handle the categorisation need.

Recurring tasks (auto-creation)

Sounds efficient, but recurring auto-created tasks quickly become background noise that no one takes seriously. Daily Update type tasks already serve this need without auto-creation complexity.

Analytics dashboards and charts

Premature. You have no baseline data. A simple list view with filter and export is more useful in Month 1 than a chart showing trends that don't yet exist. Defer to Phase 2.

Multiple assignees on one task

Destroys accountability. If two people own a task, no one owns it. If a task genuinely involves two people, it should be two tasks with clear individual ownership.

One principle to govern every future decision

Every feature in this system must make it harder to avoid accountability and easier to give an honest update — in that order of priority. If a feature makes it easier to look busy without being productive, it does not belong in this system regardless of how useful it appears on paper.
